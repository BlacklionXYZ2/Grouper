## 20:58 — Review fixes: stop threads on disconnect, admin tokens, no secrets in thread shells

- **Agent:** Claude Code · claude-opus-5-5
- **Asked by:** Oscar: fix the two most serious review findings: threads keep running on a device after it disconnects, and every device token is a full admin token (readable from a thread's shell).
- **Changed:**
  - `crates/core-client/src/lib.rs` — `Threads` no longer relies on `Drop` (each running thread holds an `Arc` to it as its host, so it never dropped). A `StopOnDisconnect` guard in `connect_once` calls `Threads::shutdown()` when the connection ends or the client is shut down: it stops every thread and drops every pending approval sender, so a waiting `approve` resolves as a denial. A `closed` flag refuses later approvals and stops a thread that starts after shutdown. New test `disconnect_stops_threads_and_denies_approvals`.
  - `crates/core-agent/src/tools.rs` — `run_shell` removes every `GROUPER_*` variable (token, provider key, hub settings) from the child's environment (`secret_env_keys`). New test `shell_hides_grouper_secrets`.
  - `crates/hub/src/db.rs` — `devices.admin` column (added to old databases on open; existing tokens become plain device tokens); `authenticate` returns `Auth { device_id, admin }`; `add_device(…, admin)`; `set_admin`. Tests for both and for the migration.
  - `crates/hub/src/server.rs` — new `admin!` check (403). Admin only: tool permissions, approvals, providers (list and set), models (add and delete), chat, thread message/stop, direct device calls. Any valid token: connect, devices, tools list, models list, conversations, events, threads.
  - `crates/hub/src/main.rs` — `grouper-hub device add --admin`, `grouper-hub device admin <id> [--off]`; `device list` shows the token kind.
  - `README.md` — the chat client's token is added with `--admin`; explains the split.
- **Why:** with the cycle, `Drop` never ran, so after a disconnect threads kept calling the model and tools while the hub showed them failed, and a thread waiting on approval hung forever. A guard owned by the connection future runs on both return and cancellation. For tokens: the shell inherited `GROUPER_TOKEN`, Auto allows `printenv`/`python3 -c`, and any token could approve calls or set Bypass, so a prompt-injected thread could raise its own access. Stripping the env closes the direct leak; admin-only endpoints mean a device token alone can't change access. Chat, thread steering and direct device calls are admin-only too, because they act for the user (direct calls skip permission levels). Reads stay open to device tokens so `grouper threads`/`watch` work from a node. Existing tokens aren't grandfathered as admin, since that would keep the hole open.
- **Verified:** `cargo build --workspace` and `cargo clippy --workspace --all-targets` clean. `cargo test --workspace --no-fail-fast`: all pass except `core-agent tools::tests::workspace_confinement`, which also fails on the untouched code on Windows (`list_files` prints `a.txt`, the test expects `a/b.txt`). Live check on Windows: a device token gets 200 on `GET /v1/devices` and 403 on set-permission, approval and providers; an admin token gets through.
- **Open:**
  - After upgrading, run `grouper-hub device admin <id>` for your own client's token (or add a new one with `--admin`). Until then nothing can approve calls or chat.
  - Devices still receive every provider API key over `/v1/connect` (by design), so a thread that reads process memory or the device's files could still get those keys. The token is also still in the CLI's own process environment and in the Swift app's memory/config; only the thread shell is cleaned. Shell is still unsandboxed.
  - Admin tokens can still connect as devices. Nothing stops someone running `grouper connect` with one, so the README warns against it.

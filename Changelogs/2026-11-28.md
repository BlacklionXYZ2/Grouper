## 13:00 — Hub side of the relay (connector, admin endpoints, CLI)

- **Agent:** Claude Code · claude-sonnet-5-5
- **Asked by:** build the hub's half of `docs/relay-design.md` in `crates/hub` (the Cloudflare Worker in `relay/` is built separately).
- **Changed:**
  - `crates/hub/src/relay.rs` — new. Settings in `hub_meta` (`relay_url`, `relay_enabled`, sealed `relay_hub_secret`, `relay_account_email`); `GET/PUT/DELETE /v1/relay`, `POST /v1/relay/nonce`, `POST /v1/relay/link` (admin only); the supervisor that dials `<relay>/relay/v1/hub/connect` with the hub secret and `Grouper-Hub-Id`, sends `hello`, serves `req` frames (one task each, aborted by `cancel`, redirects off, body streamed back in chunks of at most 48 KiB) and `ws_open` frames (a loopback WebSocket with the forwarded headers, both ways), pings every 30 s, reconnects 1 s to 60 s, stops on shutdown or step-down, and on close code 4001 shows "replaced" and waits instead of retrying. Relayed requests get `x-forwarded-for`/`cf-connecting-ip` set to the relay's client IP (the last `x-forwarded-for` entry; `0.0.0.0` if missing or loopback), `x-forwarded-proto` and `x-grouper-relayed: 1`. 22 tests with a fake relay and an in-process hub.
  - `crates/hub/src/google_auth.rs` — test hooks `GROUPER_GOOGLE_JWKS_URL` and `GROUPER_GOOGLE_AUTH_URL` (commented as test-only); new `verify_owner_token` (signature, aud, exp, owner `sub`, no hub nonce) used by `POST /v1/relay/link`.
  - `crates/hub/src/host.rs`, `server.rs`, `lib.rs` — the relay supervisor is spawned next to the tunnel's with the hub's loopback address and stopped with it; `Hub.relay` state; routes merged.
  - `crates/hub/src/main.rs` — `grouper-hub relay status` and `grouper-hub relay unlink`.
  - `crates/hub/Cargo.toml` — `tokio-tungstenite` moved from dev-dependencies to dependencies.
  - Fast-forwarded this worktree branch to `harness` first: the spec (`docs/relay-design.md`) was only there.
- **Why:** lets phones and browsers reach the hub away from home through an outbound connection, with no domain or tunnel. The relay only routes; the hub still authenticates every request, so relayed traffic must look remote (no loopback-only sign-in in local mode).
- **Decisions beyond the spec:** `PUT /v1/relay` refuses (409) a different `url` while the hub is linked (the secret belongs to the old relay); `DELETE /v1/relay` clears the link locally even if the relay can't be reached and adds `relay_forgot_hub` to the status; the supervisor re-reads settings every 30 s so `relay unlink` on the CLI (which edits the database of a running hub) takes effect; linking needs the relay address set first (400 otherwise).
